# ARIADNE 개발 계획

기준일: 2026-10-01, Asia/Seoul

상태: 사용자와 합의한 개발 계획. 앱 구현·연동·성능 검증 완료를 뜻하지 않음.

> 2026-10-01 개발 방향: 웹 버전을 먼저 개발하고, 웹의 핵심 업무 흐름을 검증한 뒤 Godot 클라이언트를 추가한다. 현재 [v0.1 1주차 기반](V0_1_FOUNDATION.ko.md)의 데이터 계약·SQLite·이력·Python 로컬 API/CLI와 Godot 시제품 코드가 구현되어 있다. 웹 화면은 아직 구현하지 않았다. [검증 기록](VALIDATION_V0_1.ko.md)에 따라 기존 구현의 완료 항목을 유지하되, 웹 화면 기반과 회사 연결 조건이 남아 있으므로 v0.1 전체 완료로 표시하지 않는다. Godot의 추가 검증은 웹 MVP의 선행조건이 아니다.

## 1. 목적과 첫 실사용 목표

AI가 업무 자료를 계속 읽고 반복적인 정리·추적·준비를 처리하며, 사용자에게는 판단과 승인이 필요한 업무를 모아준다. 성공 여부는 사용자가 직접 입력·재탐색·검토해야 하는 시간이 실제로 줄어드는지로 평가한다.

첫 실사용 목표는 메일함을 다시 뒤지지 않아도 처리할 일, 기다릴 일, 확인할 근거가 자동으로 정리되는 상태다. AI가 만든 목록을 매번 전부 확인하도록 만드는 대신 검증된 내부 작업을 자동 반영하고 예외를 모아 보여 준다.

최종 형태는 팀이 공유하는 인터랙티브 웹 대시보드다. Windows 업무환경의 브라우저와 한국어를 우선하며, 사용자 확정값과 원본 자료를 보존한다. 이후 Godot 클라이언트를 추가하더라도 웹을 유지하고 공통 업무 처리 서비스·API·데이터를 함께 사용한다.

## 2. 현재 상태와 시작 자료

- 저장소에는 기획 문서, v0.1 업무·근거 데이터 계약과 가상 예제, Python 서비스·저장 계층, Godot 시제품과 초기 백서 PDF 생성 코드가 있다.
- 로컬 기반의 구현 현황은 위 v0.1 안내를 따른다. 실제 계정 연동, AI 업무 추출과 외부 자동 실행은 아직 구현·검증되지 않았다.
- 사용자가 개발 프로그램 설치를 완료했다고 알렸다. 웹 개발·브라우저 실행 환경과 회사 계정의 연결 조건은 v0.1에서 확인하고 실제 Graph 연동은 v0.3에서 검증한다.
- 기획 당시 자료 목록에는 메일 ZIP 5개 안의 `.msg` 파일 523개, 주간업무회의 엑셀 3개가 기록돼 있다. 현재 전달된 자료의 존재·완전성은 가져오기 단계에서 별도로 확인한다.
- 523개는 당시 압축파일 내부 항목 수이며 이번 구현에서 다시 집계한 결과가 아니다. 중복 제거, 본문·첨부 분석, 정답 라벨링을 수행한 수치도 아니다.
- 과거 자료에는 분석 기준시각을 표시한다. 과거에 회신 대기였다는 사실을 현재 미처리 상태로 단정하지 않는다.
- 계약 일정 검증에 필요한 최종 날인 계약서와 변경계약 표본의 확보 여부는 별도 확인한다.

원본은 수정·삭제하지 않는다. 원문·추출 결과·AI 판단·사용자 확정값은 구분해 저장하며, 업무마다 원본 파일·메일 스레드·첨부·페이지·조항 등 검증 가능한 근거를 연결한다.

## 3. 자동화 범위

| 업무 | 목표 처리 방식 | 사용자 개입 |
| --- | --- | --- |
| 메일·첨부 수집, 펀드 분류, 동일 업무 연결 | 선택한 원천을 수집하고 근거와 함께 정리 | 펀드·업무 연결이 모호하거나 병합 충돌이 있을 때 |
| 요청·담당자·기한 파악 | 본문·첨부·상대방·시각·이전 회신을 함께 분석하고 규칙 검사 | 담당 미지정, 날짜·금액 충돌, 근거 부족 시 |
| 회신 대기·자료 수령·진행 추적 | 새 사건을 기존 업무에 연결하고 검증된 상태 전이 반영 | 내용 검토·최종 판단이 필요한 경우 |
| 결산·분배·보고 준비 일정 | 확정된 계약 규칙에 따라 생성 | 최초 규칙 확정, 변경계약 충돌 시 |
| 업무일지·주간회의 자료 | 메일 수가 아닌 실제 업무 단위로 자동 초안 작성 | 공유 전 필요한 부분 확인 |
| 회신·자료요청·보고서 준비 | 초안, 근거와 첨부 후보 준비 | 수신자·본문·첨부 확인과 발송 승인 |
| 완료 처리 | 업무별 완료조건과 증거 검사 | 검토·승인이 완료조건인 업무 |
| 자금집행·운용지시·외부 일정 변경·원본 삭제 | 자료 준비·점검 지원 | 실제 실행 전 명시적 승인 |

초기 버전에 원본 삭제·변경 기능을 넣지 않는다. 외부 발송·변경 기능을 나중에 도입하더라도 실행 전 명시적 승인 조건을 유지한다. 이 개발 계획을 승인한 사실이 개별 업무의 외부 실행 승인을 대신하지 않는다.

### 자동화 수준 확대

1. **검증 단계:** 과거 사례에서 AI 판단과 실제 처리 내역을 비교한다. 누락, 잘못된 병합, 기한 오류와 완료 오판을 찾는다.
2. **제한적 자동화:** 통과한 업무 유형의 분류·활동 기록·확정 규칙 기반 일정은 내부 데이터에 자동 반영한다. 모호한 항목은 확인 요청으로 보낸다.
3. **지속 운영:** 새 자료에 따라 기존 업무와 준비 자료를 갱신한다. 사용자 확정값과 충돌하면 자동 덮어쓰기 대신 수정 제안을 남긴다.

자동 처리 권한은 업무 유형별 평가 결과, 근거 충족 여부, 오류 영향으로 결정한다. 모델이 출력한 자신감은 정답 확률이나 실행 권한으로 취급하지 않는다. 검토 요청은 업무 단위로 묶고 변화가 없는 요청을 반복하지 않는다.

### 날인본 수령 예시

날인 요청 발송 → 진행 중 → 외부 회신 대기 → 회신·첨부 연결 → 검토 필요 → 서명·날인·첨부 이상 여부 검토 완료 → 완료.

요청 발송 또는 파일 도착만으로 최종 완료 처리하지 않는다. 부족한 근거가 있으면 확인 필요 또는 완료 추정으로 표시한다.

## 4. 데이터와 판단 원칙

v0.1에서 다음 업무 상태를 정의한다: 신규, 검토 필요, 진행 중, 내부 승인 대기, 외부 회신 대기, 일정 확정 대기, 완료, 보류, 기한 초과, 재개, 취소. 기한 초과와 대기 사유를 함께 보존할 수 있도록 상태와 기한 위험의 표현 방식을 설계한다.

업무에는 펀드·자산·담당자·관계기관·선행조건·필요자료·완료조건·기한·신뢰도·근거를 연결한다. 펀드의 한글명·영문명·약칭·SPC는 별도 펀드로 중복 생성하지 않도록 식별자와 별칭으로 관리한다.

주요 설계 항목은 다음과 같다. 이는 구현된 DB 테이블 목록이 아니다.

- 원천 식별자, 파일 해시, 스레드 관계, 수집 시각·버전·접근권한
- 업무와 활동 사건, 근거 연결, 추출 결과와 모델·규칙 버전
- AI 제안값과 사용자 확정값, 변경 충돌 및 검토 상태
- 날짜·기간·반복·사건 의존 기한, 원문·기준일·준비기간·실제 마감일
- 실행 작업의 식별키, 처리 결과, 재시도, 승인 및 중복 실행 방지
- 변경 시각·주체·이전값·새값·근거·사유를 포함한 이력

제목만으로 같은 업무를 합치지 않는다. 재송부·전달·제목 변경은 스레드·본문·첨부·상대방 등으로 판단한다. 동일 파일·메일의 재수집은 중복 반영하지 않고, 모호한 업무 병합은 확인 대상으로 둔다.

날짜만 있는 기한은 Asia/Seoul의 날짜로 보존한다. 명시되지 않은 날짜·금액·담당자·반복주기를 만들지 않는다. 월말·윤년·영업일·사건 의존 일정은 검증된 코드와 확정된 달력·규칙으로 계산한다.

미래 의무는 최종 날인 계약·정관과 정식 변경, 공식 결의·동의, 확정 안내 메일 등의 효력과 최신성을 비교한다. 실제 완료는 운용지시·지급내역·날인본·제출확인 등 직접 증거와 상대방 처리 완료 회신을 우선한다. 자료가 충돌하면 하나를 임의로 선택하지 않고 근거와 차이를 제시한다.

우선순위는 계약상 기한, 자금 영향, 투자자 대응, 내부 승인, 선행조건, 지연 위험, 재촉과 담당 공백을 종합한다. 메일의 최신성만으로 정하지 않는다.

## 5. 기술 구조와 화면

처리 흐름은 자료 수집 → 정규화 → AI 해석 → 업무 규칙 검사 → 내부 자동 반영 또는 확인 요청 → 변경·실행 이력 기록이다.

| 구성 | 역할 및 결정 상태 |
| --- | --- |
| 웹 화면 | 먼저 개발하는 기본 클라이언트. 오늘 할 일·업무 흐름·펀드 현황·근거 열람. 프레임워크는 아직 확정하지 않음 |
| 업무 처리 서비스 | Python 3.12 이상으로 로컬 API/CLI 기반 구현. 수집·AI 분석·상태판정·일정 계산·실행을 화면과 분리하여 단계적으로 추가 |
| 개인 파일럿 저장 | SQLite 저장·변경 이력·복구 기초 구현. 원본·추출·판단·확정 데이터 구분 원칙 유지 |
| Godot 화면 | 웹 핵심 흐름 검증 후 추가하는 별도 클라이언트. 기존 시제품을 보존하고 공통 API·데이터 재사용 |
| 팀 운영 | 승인된 중앙 서비스·DB·인증·권한. 공유 폴더의 SQLite 파일을 다중 사용자가 직접 수정하지 않음 |
| 연동 | 과거 MSG 가져오기 우선, Microsoft Graph 기반 수신·발신 메일 증분 수집 |
| AI 연결 | 교체 가능한 모델 연결 계층. 허용 자료와 실제 한국어 추출 평가에 따라 선정 |

웹의 한글 입력, 긴 목록 검색·필터, 키보드 조작, 복사, 근거 문서 열람과 Windows 브라우저 사용성을 먼저 검증한다. 로컬 API는 현재 단일 사용자용이므로 웹 화면의 제공 방식과 브라우저/API 경계를 먼저 설계한다. 팀 공유에는 중앙 서비스·인증·권한을 추가해야 한다.

웹 UI를 Godot UI로 자동 변환하는 방식은 전제하지 않는다. Godot의 화면·입력·내비게이션은 별도로 구현하고, 업무 규칙·JSON API·데이터 계약·근거·이력은 공통 계층에서 재사용한다. 기존 Godot 시제품과 엔진 CI 통과 기록은 후속 개발의 출발점으로 보존한다. Godot의 한글 입력·Windows 실행·사용성과 Godot 웹 내보내기는 해당 클라이언트를 개발할 때 별도로 검증하며 웹 버전 출시 조건에 포함하지 않는다.

화면은 다음 다섯 메뉴로 제한한다.

1. Command Center: 오늘 할 일, 기한 초과, 신규 요청, 회신·승인 대기, 위험 신호
2. Calendar: 과거 활동, 확정·예상·반복 일정, 펀드·담당자 필터
3. Funds: 펀드 기본정보·계약조건·관계기관·일정·업무·활동·문서
4. Work Queue: 전체 업무, 필터, 선행·후속 업무, 완료조건
5. Evidence & Audit: 근거, 상태·사용자 수정 이력, AI 추출·신뢰도, 충돌

v0.1에서 웹 클라이언트 구조와 가상 업무용 최소 화면 기반을 마련하고, v0.2에서 메일 가져오기와 연결된 웹 조회·수정 흐름을 제공한다. v0.5에서 다섯 메뉴의 전체 웹 흐름을 완성한다. 기본 이력과 데이터 보호는 v0.1부터 구현하고 v0.6에서 팀 단위로 확장한다. 현재 웹 화면은 미구현이며, Godot 추가 시점은 웹 핵심 흐름 검증 후 별도로 정한다.

## 6. 운영·연동·데이터 경계

- Microsoft Graph는 선택한 사서함·폴더 범위로 연결하고 수신·발신을 함께 추적한다. 폴더별 진행점은 수집·저장이 성공한 범위에서 확정한다.
- 회사 계정의 실제 권한과 접속 가능성을 검증한다. 연결이 지연되면 MSG 가져오기로 개발·파일럿을 계속한다.
- UI 창과 처리 서비스의 수명은 분리한다. 초기에는 PC의 처리 서비스가 실행 중일 때 수집하고 중단 기간은 재실행 후 따라잡는다.
- PC 종료 중의 상시 처리는 회사가 승인한 서버가 있어야 가능하다. 승인·운영 체계가 없는 상태에서 24시간 자동화를 약속하지 않는다.
- 부분 실패·인증 만료·요청 제한·오프라인 상태를 표시하고 제한된 재시도와 재처리로 복구한다. 마지막 수집 성공 시각을 표시한다.
- 외부 AI에는 회사가 허용한 자료만 전송한다. 외부 AI 사용이 불가하거나 장애가 나면 수동 관리와 확정 규칙에 의한 처리를 유지한다.
- 메일·첨부에 포함된 지시문은 자료로 취급한다. 앱 권한, 전송 대상과 승인 조건을 바꾸는 명령으로 실행하지 않는다.
- 원본·운영 DB·토큰·원문 로그는 Git에 포함하지 않는다. 승인된 저장 위치, 최소 접근권한, 백업·보존·비밀정보 관리 방식을 구현 전에 확정한다.
- AI 호출 비용·빈도 상한, 자동 실행 중단과 실패 통지를 둔다. 문서 작성만으로 유료 사용이나 자료 전송이 승인된 것으로 간주하지 않는다.

## 7. 버전별 로드맵

아래 일정은 개발에 집중할 수 있고 필요한 계정 접근이 확보된다는 가정의 추정치다. 시작일이 확정된 납기 약속이 아니며 완료조건을 통과한 뒤 다음 범위를 연다.

| 버전·예상 시점 | 구현 범위 | 완료조건 |
| --- | --- | --- |
| v0.1 · 1주차 | 요구사항·업무·근거·일정·상태·자동화 규칙 설계, Python·SQLite 기반, 웹 클라이언트 구조와 최소 화면 기반 | 제안·확정값 분리, 변경 이력, 웹의 가상 업무 입력·조회·수정·저장·재실행 확인, 회사 연결 조건 기록 |
| v0.2 · 2~3주차 | 과거 메일 가져오기, 스레드·업무 연결, 요청·기한·대기 추출, 활동 기록, 최소 웹 업무 흐름 | 재수집 중복 방지, 웹에서 원문 근거 열람·상태 수정·보존, 대표 정답 사례 대조 |
| v0.3 · 4주차 | Outlook 증분 수집, 자동 분석, 실패 재처리 | 회신이 기존 업무에 반영되고 장애·오래된 데이터 표시, 중단 후 재개 검증 |
| v0.4 · 5~6주차 | 계약문서 기반 일정·반복 의무, 변경계약 충돌 | 문서·조항·규칙 연결, 월말·윤년·영업일·조건부 일정 검증 |
| v0.5 · 7~8주차 | 웹 기반 인터랙티브 대시보드 | 오늘 할 일→상세→근거→수정 흐름, 다섯 메뉴, Windows 브라우저·한국어·키보드 사용성 검증 |
| v0.6 · 9~10주차 | 팀 공유·권한·중앙 저장·감사·복구 확장 | 권한 밖 자료 접근 차단, 동시 수정 충돌 처리, 백업 복원 검증 |
| v0.7 · 11~12주차 이후 | 회신 초안·보고 준비·알림·검증된 반복 업무 실행 확대 | 실행 결과 확인, 승인 연결, 중복 실행 방지, 실패 중단·재처리·통지 검증 |

초기 백서의 M0~M5와 6주 일정은 이 로드맵으로 대체한다. Godot 추가 개발은 웹 핵심 흐름이 검증된 뒤 별도 우선순위와 일정으로 진행한다. 기존 웹 클라이언트를 유지하며 같은 API의 상태·근거·이력·수정 충돌 규칙을 두 클라이언트에서 검증한다. Teams·Sheets 추가 연동과 보조 모델 비교 실험도 핵심 메일·계약 흐름을 검증한 뒤 필요성이 확인되면 별도로 우선순위를 정한다.

## 8. 첫 개발 묶음

1. 웹 우선 개발·후속 Godot 확장 방향으로 README·계획·백로그를 정리한다. 이번 문서 변경의 범위다.
2. 기존 Python API·데이터 계약에 연결하는 웹 클라이언트 구조와 가상 업무 입력·조회·수정 화면을 구현한다.
3. 과거 메일의 중복·손상·인코딩·스레드 연결 가능 여부와 첨부 형식을 점검하고, 대표 업무의 담당자·기한·완료조건·실제 처리 결과를 정답 사례로 작성한다.
4. 원본을 보존하는 업무·근거·변경 이력 저장 구조를 검증한다.
5. 웹에서 메일 가져오기 → 업무 생성 → 근거 확인 → 상태 수정 → 재실행 후 보존까지 한 흐름을 완성한다.

2026-10-01 기준 4의 기본 저장·이력과 API/CLI·Godot 시제품의 가상 업무 조회·수정·보존은 구현했다. 2의 웹 화면은 다음 구현 대상이며, 3 및 5의 실제 메일 가져오기·업무 추출은 v0.2 후속 작업이다. 스키마와 가상 예제는 현행 v0.1 계약으로 갱신했으며 팀 권한·계약 일정 실행은 아직 구현하지 않았다.

## 9. 검증과 성공 기준

검증용 정답은 사용자 또는 업무 담당자가 확인한다. 같은 스레드를 규칙 조정용과 최종 평가용에 나눠 넣지 않는다. 모호한 날짜, 과거 인용문, 여러 업무·펀드, 연기, 변경계약, 회신 없는 발송, 첨부만 도착한 경우를 포함한다.

| 대상 | 목표·검증 방식 |
| --- | --- |
| 재수집 중복·사용자 확정값 보호 | 검증 사례에서 중복 생성과 무단 덮어쓰기 0건 |
| 기한·완료 판단 | 검증 사례에서 근거 없는 확정·완료 처리 0건 |
| 근거 | 모든 판단에서 근거 또는 부족한 근거 확인 가능 |
| 업무 추출 | 중요한 요청의 누락률, 잘못 만든 업무, 잘못된 병합을 별도 보고 |
| 사용자 부담 | AI 제안 수정·승인·입력·재탐색 시간을 모두 포함해 측정 |
| 일정 | 월말·윤년·영업일·사건 의존·변경 충돌 사례 통과 |
| 운영 | 인증 만료·부분 실패·중복 재시도·백업 복원·동시 수정·권한 검증 |
| 효과 | 도입 전 5영업일과 파일럿 10영업일을 비교해 관리 시간을 30% 이상 줄이는 초기 목표 |

0건과 30%는 검증 목표이며 현재 성과나 실제 운영 무오류 보장이 아니다. 표본 수, 제외·실패 사례와 평가 기준을 함께 기록한다. 통과하지 못한 업무 유형은 자동 반영 범위를 확대하지 않는다.

## 10. 버전 기록과 남은 결정

각 버전에는 변경 목적, 추가·수정 기능, 데이터 구조 변화, 실제 검증 결과, 알려진 한계, 다음 과제를 남긴다. 계획 문서 커밋은 v0.1 앱 완성을 의미하지 않는다.

Python·SQLite 기반은 구현했고, v0.1의 남은 사항은 웹 프레임워크와 화면/API 제공 방식 결정, 가상 업무용 웹 화면 검증, 회사의 Graph 연결 조건·승인된 저장 위치·AI 전송 범위 확인이다. 실제 Graph 연결은 v0.3에서 검증한다. 계약 일정 단계에는 최종 문서 표본과 영업일 기준이 필요하다. 팀 운영에는 서버·인증·운영 담당과 복구 책임이 필요하다. Godot의 최종 채택 범위·배포 방식·플랫폼 사용성은 후속 클라이언트 개발 시 결정한다.
