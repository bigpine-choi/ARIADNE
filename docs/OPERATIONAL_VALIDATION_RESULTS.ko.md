# 운영 검증 기능 구현 및 검증 기록

2026-10-02의 운영 검증 구현과 오멘 연결 복구 기록이다. 아래 로컬 회귀·현장 확인 결과는 원격 CI와 배포본 갱신 여부를 대신하지 않는다.

기준 저장소는 `bigpine-choi/ARIADNE`, 최초 기준 main 커밋은 `e615d5adbd20b92f2160af180faa5bd7815071ee`이다. GitHub에서 읽은 원본 80개 파일을 별도 기준본으로 복원했고 각 파일의 Git blob SHA가 원격 트리와 일치함을 확인했다. 이후 운영 검증·OpenAI 연결 진단·수집 실행과 보고 양식 복구를 추가했다.

## 구현한 동작

- 이번 보고 기간의 회사 금요일 보관본, 회사 Excel 양식, 자료 수집 확인 기록을 검증한 뒤 발송 없이 보고서를 생성한다.
- 실제 수집 실패는 보고 생성을 차단한다. Teams 화면 범위 등 알려진 한계는 해당 실행에서 사용자가 확인하도록 하며, 일반 부분 보고 설정으로 실패를 우회하지 않는다.
- 사용자가 검토한 보고서의 실행번호, 본인 메일 주소, 보관 버전과 SHA-256을 고정한다. 발송 승인 후 DB에서 한 번만 발송을 점유하고 보관된 바이트를 첨부한다.
- Outlook 발송 접수와 받은편지함 도착을 별도 상태로 기록한다. 실행번호, 발신자, 단일 수신자, 첨부 이름과 바이트가 맞아야 도착 확인 완료로 처리한다.
- 발송 결과 불명확, 발송 중, 발송 접수 상태를 자동 재발송 가능한 상태로 돌리지 않는다. 늦게 종료된 발송 작업이 이미 확인된 도착 상태를 덮어쓰지 않는다.
- 화면 재접속 후 기존 실행을 선택해 처리를 이어간다. 미발송 보고서를 다시 선택하면 발송 승인은 해제되어 있다.
- 이번 주 수집 확인 기록의 고정 버전이 과거 누적 메일 10,000건의 목록 한도 때문에 차단되지 않도록 했다. 수정 전 실패한 회귀를 수정 후 통과시켰고, 실제 10,001건 수집 확인 기록과 확인 기록 없는 목록 한도의 차단도 검증했다.
- 보관 자료를 보고서 입력으로 읽을 때 과거 버전을 최신 버전으로 재삽입하거나 분석용 표시를 원본에 저장하지 않는다.
- 실제 Windows PowerShell 5.1의 실행 정책과 클래식 Outlook 설치·등록을 읽기 전용으로 확인한다. 회사 정책이 허용할 때 검증된 로컬 스크립트만 자식 프로세스의 `RemoteSigned`로 실행하고 Windows에 저장된 정책은 유지한다. 부모 PowerShell 7의 모듈 경로로 인한 5.1 보안 모듈 로딩 실패도 막는다.
- 발송 시도가 시작되기 전 확정된 설치·정책 장애는 보고서를 `prepared`로 유지한다. 실제 시도 이후의 불명확한 발송을 재시도 가능한 상태로 돌리지 않는다.
- 보관 Excel 양식의 바이트 입력과 SHA-256 표시, Windows 가상환경의 Godot 검사 서비스 PID 확인·종료 처리를 보완한다.
- 키 암호화 준비와 OpenAI 인증·모델 조회를 구분한다. 별도의 모델 조회는 사용자가 실행하며 업무 자료를 보내거나 보고를 생성하지 않는다.

데이터는 기존 `archive_scans`와 `weekly_runs.detail`에 추가한다. 테이블 추가나 스키마 마이그레이션은 없다. 비밀 저장 방식과 회사 실행 정책은 변경하지 않았다.

## 실행한 검증

실제 Windows 사용자 환경의 Python 3.13.16에서 `python -m unittest discover -s tests -v`를 실행했다. cryptography 50.0.2를 사용해 프로젝트가 선언한 최소 버전을 충족했다.

| 전체 회귀 | 통합 클론에서 320개 모두 통과, 24.528초 |

## 오멘의 실제 읽기 확인

2026-10-02 오멘에서 클래식 Outlook 설치와 설정한 본인 계정의 프로필 일치를 확인했다. 최근 1시간을 대상으로 수신 메일 2건을 읽었으며 읽기 오류는 0건이었다. 이 점검의 메일 발송과 AI로 업무 자료 전송은 모두 0건이다. 메일 주소·본문·첨부·개인 경로·인증 정보는 이 기록과 저장소에 포함하지 않는다.

이 결과는 제한된 시간의 메일 읽기 확인이다. 전 사서함·첨부 본문·전체 주간 수집의 완전성, 실제 보고 생성·도착 확인·예약 운영을 증명하지 않는다.

## 초기 샌드박스 검증 이력

2026-10-02 초기 Python 3.12.14 샌드박스에서는 268개 중 263개 통과, 실패 1개와 오류 4개가 발생했다. 당시 신규 78개는 통과했으나 아래 기존 테스트 5개는 Windows `CryptProtectData` 접근 제약으로 원본에서도 실패했다. 실제 Windows 사용자 환경에서 재실행해 암호화·복호화와 해당 테스트가 통과했으며 최신 320개 회귀에도 포함했다. DPAPI 보호를 약화하거나 평문 저장으로 우회하지 않았다.

- `test_hiworks.CredentialTests.test_corruption_blocks_call_and_does_not_echo_key`
- `test_hiworks.CredentialTests.test_dpapi_restart_replace_remove_and_ciphertext`
- `test_hiworks.CredentialTests.test_reporting_uses_saved_key_without_environment_and_without_real_call`
- `test_hiworks.CredentialTests.test_saved_key_automatically_used_in_new_process`
- `test_hiworks.ApiTests.test_http_key_saved_once_reused_and_deleted`

초기 검증 환경은 openpyxl 3.1.5와 cryptography 50.0.1을 사용했다. 최신 실제 사용자 환경에서는 cryptography 50.0.2로 재검증했으며 초기 의존성 미달 상태를 현재 결과로 취급하지 않는다.

## 아직 확인하지 못한 항목

실제 AI 보고 생성, 승인한 보고서의 메일 발송과 받은편지함 도착, 금요일 예약 실행, 오멘의 SharePoint 자료 수신, Teams 전체 주간 이력은 이번 연결 복구에서 새로 검증하지 않았다. 초기 메일 읽기 확인과 전체 회귀 통과를 이 운영 절차의 성공으로 확대하지 않는다. 새 배포본의 생성·설치와 원격 CI도 별도로 확인해야 한다.

실제 운영의 완료 조건은 회사 자료를 수신한 같은 보고 기간의 보고서를 사용자가 검토하고, 발송을 승인한 뒤, 받은편지함의 일치하는 첨부파일로 도착이 확인되는 것이다. 테스트 통과나 Outlook 발송 접수만으로 실제 운영 완료를 선언하지 않는다.
