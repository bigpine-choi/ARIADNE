# ARIADNE 코드 구조 및 데이터 설계

## 오멘·회사 PC 경계

`handoff_transport=web`은 회사 전달·오멘 수신 역할에서 허용한다. 봉인 파일은 회사 로컬 `outgoing-packets`에 유지하고 `cloud_handoff.py`가 전용 Edge 브라우저 세션의 SharePoint REST로 저장한 회사 웹 폴더에 전송한다. 브라우저의 기본 프로필·쿠키를 가져오지 않고 로그인 창의 사용자 인증은 조작하지 않는다. OS 파일 잠금으로 최초 연결과 예약 작업의 프로필 충돌을 막는다. `handoff_cloud_uploads`는 서버 바이트의 SHA-256 확인 후 기록하며 요청 결과가 불명확하면 재전송 전에 서버 파일을 확인한다. 삭제·덮어쓰기는 수행하지 않는다. 회사 폴더 URL·브라우저 세션·연결 상태는 각 PC 로컬 데이터 경로에만 둔다.

오멘의 `receive`는 같은 폴더의 파일 목록·다음 페이지·암호문만 GET한다. 다음 페이지의 호스트·경로·목록 질의를 제한하고 최대 20개씩 순번대로 로컬 `incoming-packets`에 원자 저장한다. 파일명과 인증된 본문의 stream/sequence를 대조하고 `import_packet`의 인증·해시·버전·금요일 불변 목록 검증을 재사용한다. 누락·다른 발신자·변조는 수신 실패로 표시하며 보고 직전 실패는 AI와 발송에 전달하지 않고 차단한다. 오멘 웹 수신에는 업로드·수정·삭제 요청이 없다.

`local_settings.device_role`은 단일 PC 호환 모드, 오멘, 회사 전달 PC를 구분한다. 회사 전달 역할은 메일·Teams·하이웍스·AI·발송 설정과 수동 작업을 거절한다. `handoff.py`는 폴더 스코프의 원본 버전·삭제 이력·불변 금요일 목록을 AES-GCM으로 봉인한다. DB outbox에 먼저 저장한 암호문을 동기화 폴더에 원자 게시하고 연속 순번으로 수신한다. SQLite 파일·인증 정보는 동기화하지 않는다.

오멘은 인증·용량·경로·순번·해시·버전 연속성을 검증한 뒤 자신의 DB와 관리 캐시에 반영한다. 현재 금요일 보관본을 보고 생성의 필수 선행조건으로 확인하고 해당 원본 목록의 파일과 템플릿 바이트를 사용한다. 미도착은 `weekly_runs`를 발송 상태로 만들지 않고 이후 tick에서 다시 확인한다. 중복·모호한 발송 방지는 기존 worker의 계약을 유지한다.

`desktop.py`는 최초 설정 보존·자신의 데이터 폴더를 확인하는 로컬 화면 실행·소유 사용자 예약 XML을 담당한다. 공식 Windows x64 임베디드 Python과 PyPI 해시를 확인한 wheel로 `scripts/build_portable.py`가 배포본을 조립한다. 세부 운영·복구는 [두 PC 운영](HYBRID_OPERATIONS.ko.md)을 따른다.

## 추가 구현: 하이웍스 초안·키 보관

`ariadne/hiworks.py`는 결정적인 본문 생성·금액·기간·근거 검사와 SQLite 초안 보관을 담당한다. HTTP는 기존 업무 DB의 근거 집합을 조회해 같은 함수를 호출한다. `hiworks.sqlite3`는 기존 업무 DB·자동화 DB와 별도이며 내용 해시 기준으로 초안 버전을 보관한다. 업무 상태를 수정하지 않는다.

`weekly_worker.py`는 검증한 동일 report/sources를 XLSX와 주간보고 초안에 전달하고 prepared 실행 정보에 초안 ID를 연결한다. 하이웍스 제출과 기존 본인 Outlook 발송은 다른 경로다. 새 하이웍스 외부 실행기는 아직 없다.

`ariadne/credentials.py`는 Windows 현재 사용자 DPAPI로 키를 암호화해 데이터 폴더의 `credentials/openai.dpapi`에 저장한다. 저장 키 → 기존 환경변수 순서로 조회하며 키를 HTTP 응답·로그·브라우저 영구 저장에 반환하지 않는다. 저장은 원자 교체, 손상은 명시적 실패다. 웹·CLI·예약 작업의 계정·데이터 위치가 일치해야 한다.

`web/hiworks.js`는 최초 키 등록·초안 입력·재열람·미리보기·복사·다운로드를 제공한다. 서버에서 사용자 문자열을 HTML 이스케이프한다. 기존 루프백·Host/Origin·JSON 크기 제한을 사용한다. 기안·키 HTTP 경로는 [하이웍스 안내](HIWORKS_AUTOMATION.ko.md)에 기록했다.

`web/navigation.js`는 같은 `/` 문서의 업무 목록(`#tasks`)·업무 자료(`#sources`)·기안문(`#drafts`)·주간보고(`#weekly`)·연결 설정(`#settings`) 패널을 전환한다. 메뉴 이동에서는 DOM과 기존 API·초안 저장소를 재사용해 작성 중 입력을 유지한다. URL hash로 뒤로/앞으로 가기·직접 접속·새로고침을 지원하고 알 수 없는 hash는 업무 목록으로 복귀한다. 전체 새로고침 시 저장하지 않은 입력은 유지하지 않는다. 키보드 링크·현재 메뉴 표시·제목 포커스·좁은 화면의 줄바꿈 메뉴를 제공한다. 별도 서버나 iframe은 추가하지 않는다.

공식 API용 form_id와 화면의 숫자 양식 ID를 구분한다. 페이지 연동 요청 생성 함수에는 토큰·네트워크 실행을 넣지 않았다. 첨부 누락 위험을 막기 위해 실제 인코딩 미구현 상태에서는 첨부 예정이 있는 API 패키지를 차단한다. 자동 상신·콜백 인증·상태 대사·Office Token 보관은 B46~B47에서 구현한다.

개인 보고는 금요일 16시 한국시간을 종료시각으로 연속된 7일 구간을 사용한다. `weekly_runs`의 collecting → prepared → sending → submitted 흐름에서 sending을 먼저 영속화한다. 전송 오류나 발송 후 상태 저장 실패는 delivery_unknown으로 다루며 재발송하지 않는다. 수집·준비 실패는 주별 최대 3회 자동 재시도하며 prepared 이후에는 다시 생성하지 않는다. 이 구현은 아래의 범용 승인·작업 큐 설계 전체를 충족한 것이 아니다.

로컬 70개 테스트와 Windows·Ubuntu/Python 3.12·3.14 CI가 통과했다. 실제 파일 59개·메일 110건의 제한된 수집도 확인했다. API 키가 없어 실AI·메일 발송·예약 운영은 비활성이며 Teams 전체 주간 이력은 확보되지 않았다.

## 1. 구조 결정

웹 버전을 먼저 완성한다. `feature/week1-foundation`의 Python 3.12+ 업무·SQLite 저장·서버·데모를 현재 main에서 재사용하고 회귀 검증했다. 기초 업무 서버는 표준 라이브러리 기반이며 보고용 Excel 생성에는 openpyxl을 사용한다. MSG·Graph·MCP와 완전한 Teams 이력 수집은 후속 범위다.

화면은 React·TypeScript를 기본안으로 한다. 기존 API·모델·저장소·테스트를 유지하며 모듈을 점진 분리한다. FastAPI·Pydantic·ORM 도입을 전제한 재작성이나 별도 백엔드 신설은 하지 않는다. Pydantic은 AI 추출·API 경계의 계약 검증이 필요할 때 선택적으로 검토하고 기존 스키마와 하나의 계약으로 관리한다. 서버 프레임워크 전환이 실제로 필요하면 호환성·마이그레이션·회귀 검증을 먼저 계획한다. 정확한 언어·라이브러리·모델 버전과 잠금 파일은 v0.1에서 호환성을 확인해 고정한다. 제품 버전과 각 의존성 버전은 구분한다.

서버는 하나의 저장소·배포 단위 안에 기능별 경계를 둔 **모듈형 모놀리스**로 시작한다. 작업자는 같은 코드베이스를 별도 프로세스로 실행한다. 마이크로서비스, 다중 에이전트 조직, 별도 벡터 DB를 초기 필수 구성으로 만들지 않는다.

개인 파일럿은 SQLite, 팀 운영은 PostgreSQL을 기본안으로 한다. 저장소 인터페이스와 명시적 마이그레이션으로 SQL 의존성을 제한하되, 전환이 자동으로 보장된다고 가정하지 않는다. v0.6에서 데이터 변환·권한·동시 수정·백업 복원 시험을 수행한다. 현재 파일 보관본은 별도 SQLite BLOB에 저장한다. 팀 운영의 외부 원본 저장소·권한 메타데이터 분리는 후속 설계이며 현재 구현으로 간주하지 않는다.

## 3. 데이터와 근거의 구분

| 개념 | 보존할 핵심 내용 |

| `NormalizedDocument` | 원문 순서·발신/수신·시각·본문/인용 구분·첨부 관계·파서 버전·미지원 범위 |
| `ExtractionRun` | 구조화 추출값·원문 위치·모델/프롬프트/스키마 버전·실패·검토 사유 |

정규화·추출·AI 제안을 다시 생성해도 원본과 사용자 확정값은 보존한다. 사용자 확정 필드는 AI가 덮어쓰지 못한다. 제안을 적용할 때 `expected_revision`이 다르면 충돌로 반환하고 최신 자료로 재검토한다. 업무별 수정과 감사 기록은 같은 트랜잭션에서 확정한다. 감사 로그에는 필요 이상의 원문·토큰·계좌를 복제하지 않는다.

펀드·자산·SPC·기관은 기준 식별자와 별칭으로 연결한다. 여러 화면은 같은 업무·일정을 조회하며 별도 사본을 저장하지 않는다. 원천 접근권한 변경·폐기 시 검색 인덱스와 캐시도 재평가한다.

### 업무 상태와 완료 판단

`workflow_status`는 신규·검토 필요·진행 중·내부 승인 대기·외부 회신 대기·일정 확정 대기·완료·보류·재개·취소를 지원한다. `deadline_risk`의 기한 초과를 별도 축으로 저장해 “외부 회신 대기 + 기한 초과”를 동시에 표현한다. 화면과 필터에는 사용자가 지정한 11개 상태 명칭을 모두 유지한다. 재개 이벤트에는 이전 상태와 재개 사유를 남긴다.

`completion_assessment`는 미확인·완료 추정·확인 필요·확인됨을 구분하고, 추출 신뢰도 높음·보통·낮음과 별도로 관리한다. 발송·첨부 도착은 활동 사건이며 완료 명령이 아니다. 업무별 완료조건과 필요한 증거·검토가 충족돼야 완료 전이가 가능하다. 기한 초과 계산에는 분석 기준시각을 사용하며 과거 표본을 현재 미결업무로 만들지 않는다.

## 4. 동일 메일·업무 식별과 수집

파일 가져오기→Outlook 커넥터→Graph로 원천이 확대돼도 원문 사본·정규화 메시지·업무의 식별을 분리한다. 파일 해시는 같은 바이트의 재수집만 막을 뿐 같은 메일의 모든 내보내기 형식을 식별하지 못한다.

1. 원천별 ID는 `(provider, tenant, mailbox, source_id)` 범위로 저장한다. Graph에는 지원 범위에서 Immutable ID를 요청하고 폴더 이동·원천별 ID 차이를 시험한다. 같은 사서함 내 이동과 달리 보관 사서함 이동·내보내기 후 재가져오기에는 ID가 달라질 수 있다.
2. `InternetMessageId`, 사서함, 발신·수신·시각, 본문·첨부 해시 등을 함께 비교해 동일 메시지 연결을 제안한다. 헤더 부재·재사용·서로 다른 사서함의 사본을 고려한다.
3. 제목·conversation ID만으로 업무를 병합하지 않는다. 전달·회신 관계, 내용과 첨부를 비교하고 하나의 메일에 여러 업무를 연결할 수 있게 한다.
4. 중복 여부가 불명확하면 별도 자료로 보존하고 검토 대기시킨다. 원본 접근권한은 병합된 업무로 인해 확대되지 않는다.

Graph 진행점은 사서함·폴더별로 저장한다. 원본·정규화 결과와 후속 작업의 outbox가 영속화된 뒤 해당 페이지의 진행점을 확정한다. AI 처리 완료를 수집 진행점의 선행조건으로 두지 않는다. 삭제 이벤트는 원천에서 없어졌다는 표시이며 보존 원본의 자동 삭제가 아니다. 인증 만료·제한·진행점 무효화·부분 실패는 별도 상태로 복구한다.

Outlook 커넥터는 필요할 때 검색·조회하는 실험 경로다. Graph delta와 동일한 전체성·진행점·첨부 가용성을 제공한다고 가정하지 않는다. 두 경로는 공통 정규화 계약을 사용하지만 기능 차이를 어댑터별 capability로 노출한다.

## 5. AI·검색·계산 경계

처리는 **제안 생성 → 형식·근거·업무 규칙 검증 → 정책에 따른 반영**으로 나눈다. Structured Outputs가 형식을 보장하는 범위와 실제 사실의 정확성은 구분한다. 누락·거절·불완전 응답도 성공 데이터로 저장하지 않는다. 모델·프롬프트·계약 변경 시 같은 평가자료로 회귀 검증한다.

검색 후보를 만들기 전과 모델에 문맥을 전달하기 전에 사용자·펀드·문서 권한을 검사한다. 결과를 생성한 뒤 가리는 방식에 의존하지 않는다. 초기 검색은 DB 키워드 검색으로 시작하고 필요한 경우 의미 검색을 추가한다. File Search 등 외부 검색을 쓰면 격리 가능한 저장 단위·권한 필터·삭제 및 보관 정책을 먼저 검증한다.

ZIP은 가져오기 컨테이너이며 MSG는 전용 파서로 읽는다. 압축경로 탈출·중첩·용량 제한·손상·인코딩을 검사한다. 엑셀은 시트·셀·수식·캐시값을 구분하고 PDF는 페이지·텍스트·OCR 여부를 보존한다. ZIP·MSG·엑셀을 File Search에 그대로 넣으면 완전 분석된다고 가정하지 않는다. 지원하지 않는 첨부와 OCR 신뢰도 부족을 사용자에게 표시한다.

금액·이자·보수·분배·일정은 검증된 결정적 코드로 계산한다. 금액은 `Decimal`, 통화·소수점·반올림 규칙을 명시하고 이자 일수계산·영업일 조정 규칙은 확정된 계약에서 가져온다. 시간은 UTC 시각과 원문 시간대를 보존하고, 날짜만 있는 기한은 Asia/Seoul의 날짜로 저장한다. AI는 계산 입력 후보와 설명을 제안하며 근거 없는 값은 채우지 않는다.

메일·문서 안의 지시문은 분석 자료로만 취급한다. 도구 허용목록·회사 권한·외부 전송 대상·승인 정책을 바꾸는 명령으로 실행하지 않는다. 호출량·비용 상한과 모델 장애 시 수동 처리 경로를 둔다. Batch API는 지연 허용 과거 분석에 검토하고, Agents SDK는 여러 단계 실행이 실제로 필요해질 때 도입한다. 업무 상태의 영속성은 SDK 실행 메모리에 맡기지 않는다.

## 6. HTTP·MCP 유스케이스 계약

현재 foundation 서버는 `127.0.0.1` 루프백 바인딩, Host/Origin 검사와 JSON 1 MiB 제한을 둔 로컬 실행용이다. 현행 `actorId`는 감사 로그용 이름이며 인증된 사용자 신원이 아니다. 이 상태로 외부·팀 접속을 열지 않는다. 팀 공개 전 인증·권한 경계를 추가해야 한다.

다음 함수는 예정 계약이며 실제 공개 도구가 아니다. 향후 `actor`·소속·권한은 검증된 세션에서 서버가 주입하고 모델이 넘긴 사용자 ID를 신뢰하지 않는다. 모든 쓰기는 감사·리비전 검사와 정책 검증을 통과해야 한다.

| 예정 함수 / MCP 도구 | 핵심 입력 | 반환과 제한 |
| --- | --- | --- |
| `search_evidence` | 질의, 펀드·기간, 페이지 토큰 | 권한 있는 근거 ID·발췌·원문 위치·신선도. 임의 파일경로·외부 URL 읽기 불허 |
| `get_fund_obligations` | 펀드 ID, 기간, 기준시각 | 확정/예상 일정·계산규칙·근거·미확정 사유 |
| `get_work_item` | 업무 ID | 현재 리비전·상태·완료조건·접근 가능한 근거 |
| `propose_status_change` | 업무 ID, 기대 리비전, 제안 상태, 근거 ID | 검증 결과·제안 ID. 호출만으로 상태를 확정하지 않음 |
| `apply_proposal` | 제안 ID, 기대 리비전 | 정책·확정값 보호 통과 후 변경 및 감사 ID. 초기에는 사용자 화면/내부 정책 전용 |
| `prepare_instruction_package` | 업무 ID, 확정 입력 리비전, 양식 버전 | 운용지시서·기안문·메일 초안 ID, 누락·불일치. 실제 제출·발송 없음 |
| `prepare_external_action` | 실행 종류, 확정 입력·산출물 리비전 | 정확한 대상·내용·첨부 해시·만료시각을 포함한 승인 요청 |

공통 오류는 권한 거부, 리비전 충돌, 근거 부족, 검토 필요, 지원 불가, 원천 장애로 구분한다. HTTP와 자체 MCP는 같은 유스케이스를 호출하고 별도 업무 로직을 갖지 않는다. 승인 화면이나 승인 API는 모델 도구 목록에서 분리해 모델이 스스로 승인하지 못하게 한다.

### 연동 capability와 권한

| 연결 | 초기 허용 | 포함하지 않는 기능 |
| --- | --- | --- |
| OpenAI Outlook Email 커넥터 | 공식 제공 도구의 메일 검색·목록·읽기, 실제 계정에서 검증 | 발송·삭제·증분 동기화·전체 첨부 지원을 당연시하지 않음 |

Outlook 커넥터·Graph 모두 Microsoft 인증과 테넌트 정책을 따른다. MCP는 관리자 동의나 회사 통제를 우회하지 않는다. OAuth 리프레시 토큰·API 키는 서버의 승인된 비밀정보 저장소에만 보관하고 브라우저·Godot·프롬프트·로그에 전달하지 않는다. 커넥터 실행에 필요한 액세스 토큰은 서버에서 해당 API 호출로만 전달한다.

## 7. 영속 작업과 외부 실행

이 절의 Job/OutboxEvent·실행 임대·승인 객체는 후속 목표다. 현재 구현은 위의 개인 보고 실행 상태와 본인 발송 설정에 한정된다. 본인 보고 발송도 기본 비활성이며, 임의 수신자·금액·운용지시 실행에 적용할 승인 시스템은 구현하지 않았다.

초기 작업 큐는 DB 기반 `Job`과 `OutboxEvent`로 구현한다. 상태는 대기·실행 중·재시도 대기·성공·실패·결과 불명으로 구분하고 실행 임대시간·시도 수·다음 실행시각을 저장한다. 업무 변경과 outbox 기록을 같은 트랜잭션으로 확정하고 작업자는 중복 배달을 전제로 멱등하게 처리한다. 부하 근거가 생기기 전 별도 메시지 브로커를 필수화하지 않는다.

외부 승인에는 사용자·권한·작업 종류·정확한 수신자/대상·본문·첨부 해시·payload hash·업무/산출물 리비전·유효기간을 결합한다. 수신자·금액·지급일·계좌·내용·첨부 중 하나라도 변경되면 기존 승인을 무효화한다. 실제 실행 직전에 권한·정책·승인·중복 여부를 다시 검사한다.

외부 실행이 타임아웃이면 실패라고 단정하지 않는다. `결과 불명`으로 격리하고 외부 처리 ID·조회·증빙으로 결과를 확인한 뒤 재시도 여부를 결정한다. 수신 시스템의 멱등 지원 없이 “정확히 한 번 실행”을 보장하지 않으며 무조건 재시도하지 않는다. 운용지시 준비와 실제 제출, 제출과 지급 완료도 각각 구분한다.

## 8. 문서 생성과 단계별 검증

운용지시서·기안문·메일은 하나의 확정된 입력 스냅샷에서 함께 만든다. 양식 버전·입력 리비전·산출물 해시를 연결하고 원본 양식은 수정하지 않는다. 엑셀은 지정 셀만 채워 수식·서식·병합·인쇄 설정·숨김/그룹을 보존하고 검증용 셀·주석을 산출물에 임의로 추가하지 않는다. 금액 합계·수신기관·날짜·필수자료를 재대사하며 렌더링·재계산 방법을 검증한다. HWP/HWPX는 별도 어댑터가 검증되기 전 지원 완료로 표시하지 않는다.
