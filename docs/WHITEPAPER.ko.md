# 펀드 운용 업무 자동화 개발계획 백서

Fund Ops Workbench | 의사결정 및 개발 착수안 | 2026년 9월 30일

## 1. 핵심 제안

Outlook의 요청과 회신, Teams의 공유 업무 목록, Google Sheets의 펀드별 일정을 연결하는 Windows 업무 보조 프로그램을 개발한다. 첫 목표는 업무를 대신 최종 결정하는 것이 아니라, 담당자가 확인할 항목을 빠짐없이 모으고 근거와 함께 정리하는 것이다.

첫 버전의 핵심 기능은 오늘 할 일, 회신 대기, 반복 일정, 공유용 업무 목록 초안이다. 메일 요약만 제공하면 기존 목록을 다시 작성하는 부담이 남는다. 따라서 원문에서 업무 후보를 만들고, 사람이 확인한 상태를 다음 날에도 이어받는 업무 기록이 중심이어야 한다.

개발은 VS Code와 TypeScript를 사용한다. Electron과 React로 Windows 앱을 만들고, SQLite에 로컬 업무 상태를 저장한다. Microsoft Graph와 Google Sheets API를 정식 연동 경로로 삼되 수동 가져오기만으로도 첫 실험이 가능하게 한다. Godot은 사용하지 않는다. OpenAI API는 문장 이해와 초안 작성용 선택 기능으로 도입하고, Jev는 정해진 범주 중 선택하는 분류용 실험에 한정한다.

이번 산출물은 기획 백서, 개발 백로그, 데이터 계약 초안과 가상 예제다. 실제 업무 앱, 계정 연동, 모델 성능 실험은 다음 개발 단계의 산출물이다.

## 2. 조사 범위와 확인된 업무

2026년 9월 30일 한국 시간 기준으로 사용자가 열어 둔 앱을 조사했다. Outlook classic의 받은 편지함 목록과 미리보기, 폴더 구조를 확인했고 Teams의 현재 업무 공유 대화와 일부 이전 메시지를 화면으로 읽었다. 모든 메일, 모든 채팅이나 첨부파일을 조사한 것은 아니다.

웨일에는 업무 일정 Google Sheets가 열려 있었다. 창 제어 도구가 창 소유자 식별 오류를 반복하여 다른 브라우저 탭까지 탐색하지 못했다. 대신 연결된 Google Drive에서 제목이 일치하고 당일 열람 기록이 있는 공유본을 찾아 메타데이터와 두 범위를 읽었다. 같은 제목의 이전 사본도 존재해, 브라우저 주소까지 대조한 동일 파일 확정은 하지 못했다.

읽은 범위는 연간 루틴업무 캘린더 A1:P36, 펀드 설정 체크리스트 A1:H30이다. 백서에는 업무 패턴만 기록하며 실제 펀드명, 거래처, 금액, 연락처와 원문 링크는 포함하지 않는다.

| 관찰 | 확인한 사실 | 설계에 미치는 영향 |
| --- | --- | --- |
| Outlook | 여러 사서함과 펀드별 폴더, 감사 자료 요청, 비용 확인, 배달 실패와 수신자 수정 관련 메일 | 사서함 범위 선택, 요청별 대기 상태, 발송 전 확인 목록 필요 |
| Teams | 날짜별 업무를 긴 텍스트 목록으로 공유하며 pending, 연기, 회신 대기 같은 상태를 기재 | 목록 자동 초안과 상태 이력, 오래된 항목 재확인 필요 |
| 문서 협업 | 공유 경로의 문서를 다른 사람이 열지 못한다는 대화가 보임 | 파일 존재와 읽기 가능 여부, 문서 형식·버전 확인 필요 |
| 일정표 | 펀드별 탭, 연간 루틴, 설정 체크리스트가 한 파일에 공존 | 화면의 표 모양과 별개로 공통 업무 데이터 구조 필요 |
| 반복 규칙 | 말일, 월말 금요일, 분기 익월, 특정 업무 후, 대략적인 시기 표현 | 날짜·기간·사건 의존 조건을 구분해야 함 |
| 시간대 | 조회한 공유본의 시간대가 America/Los_Angeles | 한국 업무일과 문서 시간대 차이를 수입 단계에서 표시해야 함 |
| 개발 환경 | Git·Node 실행 가능, Power Automate 설치 확인, VS Code·Python·.NET 명령은 PATH에서 미확인 | 개발 도구 설치는 별도 준비 작업이며 미설치라고 단정하지 않음 |

위 관찰에서 반복 입력과 확인 업무의 자동화 가능성을 추론했다. 실제 건수, 소요 시간, 누락률과 부서 전체의 업무 방식은 아직 측정하지 않았다. 일정표의 업무 표현은 운영 자료의 표현이며 법정기한이나 계약 조건을 검증한 결과가 아니다.

## 3. 자동화 우선순위

우선순위는 화면에서 반복된 패턴, 구현 난이도, 잘못 처리했을 때의 영향을 기준으로 정한 기획 판단이다. 아래 절감 시간은 측정값이 아니며 파일럿에서 확인할 가설이다.

| 순위 | 기능 | 처음 제공할 결과 | 절감 가설 |
| --- | --- | --- | --- |
| P0 | 오늘 할 일과 회신 대기 통합 | 기한·담당·대기 상대·다음 확인일·출처가 있는 목록 | 하루 10~15분 |
| P0 | 반복 일정 생성 | 승인된 규칙으로 만든 향후 업무 후보 | 하루 환산 5~10분 |
| P0 | 팀 공유 목록 초안 | 진행·대기·변경 사항을 기존 목록 형식으로 정리 | 하루 5~10분 |
| P1 | 감사와 증빙 요청 추적 | 요청자료·확보 여부·검토 여부·버전 현황 | 관련 업무가 있는 날 10~20분 |
| P1 | 발송 전 점검 | 수신자, 배달 실패 이력, 필수 첨부, 기준일 불일치 표시 | 재작업 감소로 측정 |
| P2 | 문서 비교와 보고 초안 | 승인된 두 버전의 차이와 출처가 있는 보고 초안 | 별도 실험 |

첫 파일럿은 한 사람이 사용하는 업무 목록과 소수의 선택한 일정 탭으로 제한한다. 공유 사서함 전체나 모든 Teams 채팅을 한 번에 연결하지 않는다. 사용자가 선택한 원천의 수집 상태와 마지막 성공 시각을 화면에 표시한다.

수익률 계산, 재무모델 수치 확정, 지급·운용지시, 계약·민원 회신의 최종 판단, 투자자 정보 변경은 MVP 자동 실행 범위에서 제외한다. 이들은 관련 자료와 확인 목록을 준비하는 기능으로만 다룬다.

## 4. 제품 화면과 사용 흐름

주 화면은 장식적인 대시보드보다 업무 표를 우선한다. 왼쪽에 오늘·이번 주·회신 대기·반복 일정·자료 요청을 두고, 가운데에 업무 목록, 오른쪽에 선택한 업무의 원문 근거와 변경 이력을 보여 준다. 펀드와 상태로 필터링하며 담당자를 확정하지 못한 항목은 미지정 상태로 남긴다.

아침에는 전일 이후 들어온 후보를 검토하고 오늘 할 일을 확정한다. 오전 중에는 요청한 자료의 회신 여부를 확인한다. 업무가 끝날 때 진행·완료·대기 항목을 고른 뒤 Teams에 올릴 텍스트 초안을 생성한다. MVP는 이 초안을 복사하거나 파일로 내보내는 데서 끝난다.

메일 한 통에 여러 업무가 있으면 각각 분리하되 같은 원문을 참조한다. 회신이 왔다는 사실만으로 완료 처리하지 않는다. 예를 들어 자료를 받았어도 검토는 남을 수 있으므로 수신 완료와 업무 완료를 구분한다.

상태는 후보, 확인됨, 진행 중, 외부 회신 대기, 검토 대기, 완료, 취소로 구성한다. 기한 변경은 이전 날짜, 새 날짜, 변경 사유와 원문을 함께 기록한다. 같은 내용이 메일과 Teams에 반복되어도 자동으로 삭제하거나 덮어쓰지 않고 병합 후보를 제시한다.

앱을 꺼 두었던 기간의 알림은 다음 실행 시 미처리 목록으로 모은다. 24시간 상시 감시가 필요해지면 별도 서비스 운영을 검토한다. 초기 앱이 종료된 동안에도 동기화된다고 약속하지 않는다.

## 5. IDE와 앱 기술 선택

| 후보 | 적합한 점 | 추가 부담 | 결정 |
| --- | --- | --- | --- |
| VS Code | TypeScript 편집·디버깅과 Git 작업을 한곳에서 수행 | 컴파일러와 프로젝트 의존성은 별도 설치 | 기본 IDE |
| Visual Studio와 C# | Windows 네이티브와 COM 중심 구현에 적합 | 이번 웹 UI·API 중심 구조와 언어가 나뉨 | COM 통합이 주기능이 되면 재검토 |
| JetBrains 계열 IDE | TypeScript 개발의 대안 | 기존 사용 여부·라이선스 미확인 | 필요 시 개인 선호에 따라 선택 |
| Electron + React | TypeScript로 UI·로컬 처리 공유, 데스크톱 배포 가능 | 메모리, 앱 크기와 정기 업데이트 관리 | MVP 앱 구조로 채택 |
| Tauri + React | 운영체제 WebView 활용, 가벼운 패키지 지향 | Windows 빌드에 Rust·C++ 도구 및 WebView2 고려 | 설치 크기가 실제 제약이면 재검토 |
| 브라우저 전용 앱 | 팀 배포와 접근이 간편 | 로컬 파일·공유 폴더·인증 보관 및 서버 운영 설계 필요 | 팀 확장 단계 후보 |
| Godot | 2D·3D와 장면 기반 상호작용, 일반 GUI도 제작 가능 | 메일·표·문서 중심 앱에서 게임 엔진의 이득이 작음 | 이번 프로젝트 미사용 |

Godot을 배제하는 이유는 GUI를 만들 수 없어서가 아니라 이 업무에 3D 장면, 물리 엔진, 실시간 시뮬레이션이 필요하지 않기 때문이다. 향후 부동산 공간 시각화가 별도 제품 목표가 될 때 독립적으로 평가한다. [S1][S2][S3]

런타임은 구현 시작일의 지원 중인 Node LTS와 안정 Electron을 호환성 확인 후 고정한다. React·TypeScript·SQLite의 실제 패키지 버전과 잠금 파일은 첫 구현 PR에서 생성한다. 현재 문서는 설치나 성능 측정 결과가 아니다.

Electron의 화면 프로세스는 제한된 명령만 호출하도록 하고 메일 HTML을 실행하지 않는다. contextIsolation과 sandbox를 유지하고 nodeIntegration은 끈다. 인증과 파일 접근은 앱 내부의 제한된 계층에서 담당한다. 이 구성은 구현 후 별도로 검증해야 한다. [S4]

## 6. 데이터 연결과 시스템 구조

처리 순서는 원천 선택, 변경 수집, 문서 정규화, 업무 후보 추출, 규칙 검사, 사용자 확인, 업무 상태 저장, 목록 출력이다. AI가 직접 사서함을 수정하는 구조를 두지 않는다.

| 구성 요소 | 역할 | 최초 구현 |
| --- | --- | --- |
| 가져오기 | 선택한 텍스트·CSV·메일 내보내기 읽기 | 수동 입력과 가상 데이터 |
| 연결 모듈 | Outlook·Teams·Sheets 읽기 | 회사 계정 접근 실험 후 순차 추가 |
| 정규화 | 원천 식별자, 시각, 본문, 첨부 메타데이터 분리 | HTML 정제, 날짜 원문 보존 |
| 업무 엔진 | 중복 후보, 상태 전이, 반복 규칙, 검토 큐 | 결정적 코드와 명시적 규칙 |
| 모델 연결 | 선택한 데이터의 요약·추출·분류 | 교체 가능한 인터페이스 |
| 저장소 | 업무·출처·버전·동기화 진행점 보존 | 로컬 SQLite |
| 출력 | 일일 공유 목록, 자료 요청 목록 | 텍스트와 CSV, 이후 문서 템플릿 |

Outlook은 Microsoft Graph의 선택한 메일 폴더를 읽는다. 본문을 읽을 때는 Mail.Read를 검토하며, 메타데이터만 다루는 경우 Mail.ReadBasic으로 충분한지 구분한다. 폴더별 deltaLink와 nextLink를 보관하고, 페이지 처리가 모두 성공한 뒤 진행점을 확정한다. 본문 처리에는 메타데이터 권한만으로 충분하다고 가정하지 않는다. [S5]

공유 사서함은 Mail.Read.Shared와 원래의 사서함 접근 권한을 별도로 확인한다. 개인 사서함 delta와 공유 사서함·알림의 동작을 동일하다고 가정하지 않고 제한된 목록 조회부터 검증한다. 허용된 사서함 ID를 명시적으로 저장해 다른 계정으로 범위가 넓어지지 않게 한다. [S6]

Teams는 업무·학교 계정의 위임 Chat.Read와 선택한 채팅의 메시지 조회를 검토한다. 페이지네이션과 수정 시각을 처리하고, 제한된 주기 조회·중첩 조회·ID 중복 제거로 시작한다. 삭제·편집 동기화는 재조정 정책을 별도로 시험한다. 운영 기본 경로에서 beta 전용 delta API를 전제하지 않는다. 채널은 채팅과 다른 API·권한이므로 별도 범위로 둔다. [S7]

Google Sheets는 선택한 파일·탭·범위만 읽고 원본의 수식·서식을 보존한다. API 승인 범위와 실제 파일 권한을 확인하며 서비스 계정으로 조직 자료에 자동 접근할 수 있다고 가정하지 않는다. 초기에는 읽기 전용으로, 확인된 업무 상태는 앱에 저장한다. 양방향 동기화는 충돌 해결 정책이 마련된 후에만 추가한다. [S8]

429와 일시 장애는 Retry-After 및 제한된 재시도로 처리한다. 오래된 캐시를 최신으로 표시하지 않는다. 원천의 삭제는 로컬 업무를 지우는 대신 원문 접근 불가 상태로 기록하고 관련 검토를 요청한다.

회사의 API 등록·동의가 불가능하면 수동 가져오기로 파일럿을 계속할 수 있다. classic Outlook을 대상으로 설치된 Power Automate를 보조 수단으로 검토하되, 해당 데스크톱 Outlook 액션은 새 Outlook을 지원하지 않는다는 제품 제한과 회사 라이선스를 확인한다. [S9]

## 7. 기한과 업무 상태의 데이터 설계

업무에는 업무 ID, 제목, 펀드의 내부 식별자, 상태, 담당자, 다음 확인일, 기한 정보, 원천 참조, 검토 이력을 둔다. 원천 정보에는 사서함·대화·파일의 ID, 원천 항목 ID, 수집 시각, 버전, 필요한 짧은 근거를 보존한다. 원문 전체 저장은 별도의 보존 설정으로 관리한다.

기한은 하나의 날짜 필드만으로 표현하지 않는다. 원문, 유형, 계산 결과, 시간대, 확정 여부, 사용한 규칙 버전을 함께 둔다.

| 표현 유형 | 저장 방식 | 처리 원칙 |
| --- | --- | --- |
| 명확한 날짜 | date와 원문 | 연도·시간대를 확인하고 표시 |
| 매월 말일 | recurrence와 월말 규칙 | 달 길이와 윤년을 코드로 처리 |
| 월말 금요일 | recurrence와 요일 규칙 | 해당 달의 마지막 금요일 계산 |
| 분기 익월 | 해당 월 또는 날짜 범위 | 날짜가 없으면 특정 일자로 확정하지 않음 |
| 중순 또는 월중 | window와 원문 | 운영자가 정의한 범위가 없으면 검토 필요 |
| 어떤 업무 완료 후 | event와 선행 업무 ID | 선행 업무가 확인되기 전 기한 미확정 |
| 며칠 전 또는 영업일 전 | 기준 사건과 offset | 승인된 영업일 달력과 계약 규칙 필요 |

날짜만 있는 마감은 한국의 날짜 값으로 보존하고 UTC 자정으로 바꿔 전날로 보이는 오류를 막는다. 실제 시각이 있는 사건은 UTC와 원천 시간대를 보존한다. 문서의 미국 서부 시간대는 원본을 자동 변경하지 않고 수입 시 차이를 표시한다.

반복 규칙으로 생성한 업무에는 규칙 ID와 발생 기간을 묶은 키를 둔다. 재실행해도 같은 달의 업무가 두 번 생기지 않아야 한다. 수신·자료 확보·검토 완료·최종 업무 완료를 서로 다른 사건으로 기록한다.

동일 제목만으로 업무를 합치지 않는다. 원천 ID와 업무 맥락을 우선하고, AI는 유사성 후보를 제안한다. 승인된 마감이나 완료 상태를 새 요약이 조용히 덮어쓸 수 없게 한다.

저장소의 JSON Schema는 날짜와 사건 의존 기한의 최소 계약을 보여 주는 초안이다. 전체 DB 스키마나 반복 규칙 실행기, 접근 제어 구현을 대신하지 않는다.

## 8. OpenAI API 도입 결정

OpenAI API는 선택 기능으로 채택한다. 담당 업무는 한국어·영어 혼합 문장의 업무 후보 추출, 회신 대기 사유 정리, 근거를 포함한 요약, 공유용 목록과 메일 초안 작성이다. 규칙만으로 처리되는 일정 계산과 ID 중복 제거에는 모델을 쓰지 않는다.

Responses API와 Structured Outputs를 사용해 업무 후보의 형태를 제한한다. 구조가 맞는 출력도 사실이나 날짜가 맞다는 보장은 아니므로, 원문 근거·업무 식별자·기한 검증을 별도로 수행한다. 거부, 비정상 종료와 불완전 출력은 검토 큐로 보낸다. [S10]

실제 모델은 이름의 최신성보다 한국어 추출 정확도, 수정 시간, 지연과 비용을 기준으로 선정한다. 비교 시 사용 모델 ID·버전·프롬프트·스키마를 고정해 기록한다. 이 계획 단계에서 특정 모델의 업무 성능이나 계정 이용 가능 여부를 검증했다고 보지 않는다.

API 전송은 회사가 허용한 자료 범위로 제한한다. 기본 설정은 외부 AI 비활성화이며, 사용자가 기능을 켤 때 전송 항목을 보여 준다. API 요청에는 store:false를 설정할 계획이다. 이 옵션만으로 Zero Data Retention이 되는 것은 아니며, 기본 남용 모니터링 로그 보존과 별도 승인 조건을 검토해야 한다. API 데이터의 모델 학습 사용은 기본적으로 옵트인 방식이다. [S11]

API 키는 Git이나 화면 코드에 두지 않는다. 개인 파일럿은 운영체제의 인증 정보 저장소에 보관하고, 팀 배포에서는 승인된 서버 측 프록시를 검토한다. 앱 번들에 공용 비밀 키를 넣지 않는다. 원문 및 모델 요청 로그도 저장소와 분리한다.

AI가 꺼져 있거나 장애가 나면 사용자가 업무를 직접 입력·수정하고 반복 규칙과 공유 목록 템플릿을 사용할 수 있어야 한다. API 비용이 발생하는 호출은 이번 기획 과정에서는 실행하지 않았다.

## 9. Jev 도입 결정

사용자가 설명한 도구는 TypeSafe AI의 Jev로 확인했다. 공식 문서는 이를 자유로운 문장을 생성하는 모델 대신 상태와 정해진 질문을 받아 구조화된 판단을 반환하는 System One 모델로 소개한다. Choice는 선택지, Score는 평가 단계, Noul은 명제의 참 정도를 다룬다. [S12]

따라서 Jev는 문서 작성 도구의 대체재가 아니라 업무 유형, 회신 필요 여부, 검토 우선순위를 고르는 보조 분류기로 평가한다. 펀드 선택에는 미분류 항목을 반드시 두고 여러 펀드가 언급된 입력을 억지로 하나로 분류하지 않는다. 실제 날짜·금액·담당자 문자열 추출과 한국어 초안 생성은 파서나 생성형 모델이 담당한다.

공급자는 70~500ms와 특정 System One 평가에서 40~200배 빠른 성능을 제시한다. 이는 공급자의 비교 조건에서 나온 주장이다. 한국의 네트워크 지연, 긴 메일 스레드, 한국어 업무 정확도와 전체 처리 시간을 그대로 보장하지 않는다. 자료 수집과 사용자 검토가 병목이면 모델 한 단계가 빨라도 전체 업무 절감은 작을 수 있다. [S13]

반환 형식이 제한된다는 것은 틀린 범주를 고를 수 없다는 뜻이 아니다. Choice·Score의 confidence는 분포에서 산출한 값이며 우리 업무에서의 정답 확률로 그대로 취급하지 않는다. Noul에 동일한 confidence 필드가 있다고 가정하지 않는다. 임계값은 검증 자료로 조정한다. [S14]

결정은 실험 채택, MVP 기본 경로 제외다. 규칙 기반과 OpenAI 기반 분류를 기준선으로 두고 Jev를 나란히 비교한다. 통과하면 저위험 분류에만 넣고 불확실한 경우 검토 큐로 넘긴다. Jev가 제안한 결과만으로 기한 확정, 자료 삭제, 메일 발송이나 자금 관련 실행을 하지 않는다.

실험은 정답을 사람이 붙인 비식별 업무 샘플 300건을 목표로 한다. 메일 스레드 단위로 100건은 규칙·임계값 조정, 200건은 최종 평가에 배정한다. 업무 유형, 한영 혼합, 여러 펀드, 일정 변경과 모호한 요청을 포함하며 중요 범주의 표본이 부족하면 확대한다. 같은 스레드의 회신을 양쪽에 나눠 넣지 않는다.

동일 입력과 출력 범주로 범주별 precision·recall, 긴급 건 누락, 미분류율, 사람의 수정 시간, 한국에서의 p50·p95 지연, 재시도를 포함한 총비용을 측정한다. 잠정 통과 기준은 분류 macro F1 0.95 이상, 기한 관련 중요 범주 recall 0.98 이상, 기준선보다 동일 오류 수준에서 분류 단계 p95가 30% 이상 짧은 것이다. 작은 표본의 통과가 무오류 보장은 아니므로 실제 도입 후에도 검토를 유지한다.

도입 전 TypeSafe의 데이터 보존, 로그, 하위 처리자, 리전, 계약 조건을 회사 기준으로 확인한다. 공개 개인정보 정책만으로 업무 데이터 무보존이나 국내 처리를 보장한다고 해석하지 않는다. 정책을 충족하지 못하면 Jev를 사용하지 않아도 제품이 동작한다. [S15]

## 10. 데이터 보호와 운영 원칙

관찰한 회사 메일과 대화에는 거래·법률·투자자 관련 정보가 섞여 있다. 코드 저장소는 비공개를 기본으로 하고 업무 원문을 보관하는 장소로 쓰지 않는다. 백서에는 일반화한 업무 패턴, 예제에는 가상 데이터만 둔다.

로컬 DB는 기본 SQLite만으로 암호화된다고 가정하지 않는다. 승인된 암호화 볼륨과 접근 제어를 기본 조건으로 삼고, 별도 DB 암호화가 요구되면 배포 호환성과 키 복구까지 검증한다. 캐시 보존 기간, 퇴사·기기 분실 시 처리와 백업 위치는 회사 정책에 맞춰 확정한다.

외부 메일, 첨부파일과 대화 내용은 데이터다. 그 안에 있는 지시문으로 프로그램의 권한이나 전송 목적지가 바뀌지 않아야 한다. 원문 HTML은 실행하지 않고 필요한 텍스트로 정제한다. 첨부파일 미리보기는 격리된 처리와 지원 형식부터 시작한다.

동기화 실패, 분류 결과, 사용자 수정, 기한 변경을 감사 이력에 기록하되 비밀 키와 전체 원문을 디버그 로그에 남기지 않는다. 자동 실행을 중단하는 스위치와 실패 후 재처리 큐를 둔다. 작업의 식별키를 활용해 재시도가 중복 출력이나 중복 변경을 만들지 않게 한다.

MVP 외부 연결은 읽기 중심이다. 향후 발송 기능을 추가한다면 원문·수신자·첨부·본문을 최종 검토하는 별도 실행 단계와 중복 발송 방지 장치가 필요하다. 결재와 지급 시스템은 이 앱의 자동 실행 대상으로 설계하지 않는다.

## 11. 개발 일정과 산출물

아래는 개발자 1명, 업무 담당자의 주당 약 2시간 검토, 계정 접근 확인이 지연되지 않는다는 가정의 6주 계획이다. M0에서 권한 확보가 지연되면 연동 일정은 늘어나며, 수동 가져오기 파일럿은 병행할 수 있다.

| 단계 | 기간 | 결과 | 완료 조건 |
| --- | --- | --- | --- |
| M0 | 1주차 | 실제 표본과 접근 가능성 확인, 가상 데이터, 개발 환경 | 원천별 허용 범위와 승인 담당 확인, 수동 입력 시연 |
| M1 | 2주차 | 로컬 업무 표, 상태·근거·기한·일일 목록 | AI 없이 입력·수정·저장·재실행 가능 |
| M2 | 3주차 | Outlook과 Sheets 읽기, 반복 일정 | 재동기화 중복 없음, 시간대와 변경 이력 확인 |
| M3 | 4주차 | OpenAI 후보 추출과 공유 목록 초안 | 구조 검증, 거부·장애 처리, 기한 오류 평가 |
| M4 | 5주차 | Teams 연결 실험, Jev 비교 실험 | 권한에 맞는 범위 처리, 비교 보고서, 도입 결정 |
| M5 | 6주차 | 제한된 실사용 파일럿과 배포 | 복구·백업·비용·수정 시간 측정, 배포 승인 |

각 단계는 실행 가능한 결과를 검토한 후 다음 범위를 연다. 처음부터 범용 자율 에이전트, 벡터 DB, 복잡한 다중 에이전트, Kubernetes를 도입하지 않는다. 검색량과 운영 요건이 실제로 필요성을 입증할 때 확장한다.

HWP·DSD 등 특수 문서 파싱, OCR, 공유 폴더 전체 색인, 발송 자동화, 모바일과 다중 사용자 서버는 후속 범위다. 특히 특수 문서의 공개 변환기와 라이선스·정확도는 이번 조사에서 검증하지 않았다.

## 12. 검증과 성공 기준

파일럿 직전 5영업일 동안 목록 작성·메일 재탐색·일정 확인에 쓰는 시간을 사용자가 간단히 기록한다. 이후 10영업일 파일럿에서 같은 기준으로 비교한다. 업무량 차이와 프로그램에 후보를 입력하고 수정한 시간도 포함한다.

| 검증 대상 | 합격 기준 제안 |
| --- | --- |
| 기한 추출 | 확정 제안 precision 98% 이상, recall 별도 보고, 모호한 표현의 강제 확정 0건 |
| 반복 일정 | 윤년, 월말, 마지막 요일, 영업일, 사건 의존 규칙의 승인된 사례 통과 |
| 중복과 수정 | 재수집 시 중복 생성 0건, 사람의 확정 상태 무단 덮어쓰기 0건 |
| 원문 근거 | 모든 후보에서 원천 식별·수집 시각·근거 확인 가능, 접근 실패 상태 표시 |
| 연결 장애 | 429·토큰 만료·부분 수집 실패에서 누락 경고 및 안전한 재개 |
| 효과 | 입력·검토까지 포함한 일일 관리 시간 30% 이상 감소를 목표로 측정 |
| 보안 | 키·원문이 Git에 포함되지 않음, 선택하지 않은 원천 미수집 |

98%와 30%는 실측 결과가 아니라 통과 기준 제안이다. 평가에는 날짜가 없는 요청, 일정 연기, 서로 다른 연도의 같은 월일, 인용된 과거 메일, 한 통의 여러 업무, 삭제된 원문을 포함한다. AI 기준은 전체 정확도 외에 중요한 업무 유형의 누락을 별도로 본다.

UI는 한국어 긴 제목, 작은 화면, 키보드 이동, 필터 후 빈 목록, 동기화 실패와 오프라인 상태를 확인한다. 자동 발송은 MVP에 없어 발송 권한을 필요로 하지 않아야 한다.

## 13. 비용과 경제성

월 절감 시간은 하루 순절감 분 × 월 근무일 ÷ 60으로 계산한다. 가령 하루 25분, 20일이면 약 8.3시간이다. 이는 예시이며 현재 사용자의 업무에서 입증된 결과가 아니다. 최초 개발비는 개발 일수 × 일당으로, 운영비는 API·저장·배포·유지보수 시간을 합산한다.

모델 비용은 월 요청 수 × 요청당 입력 토큰 ÷ 100만 × 입력 단가와 출력 토큰 비용, 재시도 비용을 더해 계산한다. 예시로 월 3,000건·입력 1,500토큰이면 입력 450만 토큰이다. 생성 요청이 600건·출력 400토큰이면 출력 24만 토큰이다. 실제 사용량이 아니라 예산 계산용 가정이다.

Jev의 공개 발표 단가인 입력 100만 토큰당 0.042달러를 적용하면 위 입력 부분은 약 0.189달러다. 이 값은 발표 단가를 사용한 산술 예시이며 계정 견적, 최소 과금, 변경 가격, 세금이나 다른 모델 비용을 포함하지 않는다. 현재 계약 가격과 모델별 OpenAI 가격은 구현 시 공식 가격표로 다시 확인한다. [S13][S16]

초기 파일럿의 API 예산 상한은 월 30달러를 제안한다. 이는 구매 승인이 아니다. 80%에서 알림, 100%에서 신규 선택적 AI 호출을 멈추고 수동 기능을 유지한다. 지연된 사용량 집계만 믿지 않고 앱이 요청 전에 예상 비용을 예약하는 방식도 설계한다.

6주 계획의 총 개발 투입은 약 20~30인일을 추정한다. 인건비와 유지보수가 단순 분류 API 비용보다 클 가능성이 높다. 시간이 거의 들지 않는 분류를 Jev로 교체하는 것보다, 업무 목록 재작성과 원문 재탐색을 줄이는 기능을 먼저 검증한다.
